# CSAT / Service & Experience View — Implementation Design

Status: **Phase 1 SHIPPED 2026-07-10** (`bf79ff5`): nav renamed
"Service & Experience", `csat` ready, `ref_cx_targets` seed, and all five
Phase-1 panels live in `CsatView.tsx` (KPI band, trend, channel, journey,
segmentation). **Phase 2 SHIPPED 2026-07-12** (merged to `main` via PR #12,
`24123e9`, W7): driver analysis, operational correlation, and survey health
with an NPS response-rate denominator. **Phase 3 SHIPPED 2026-07-12** (W8):
Voice-of-Customer verbatim feed + theme frequency, and the closed-loop
detractor follow-up queue, in a new "Voice of Customer" tab — see the build
notes below. Originally verified against branch `fix/csr-header-site-grain`
(tip `11d7071`, 2026-07-10).

**Phase 3 build notes (2026-07-12):**
- Verbatim text needed **no new synthetic-data generator** — `comment_text`
  already existed on `fact_survey_responses`, LLM-generated by `ai_query` at
  build time in `raw_qualtrics_response.sql` for ~5% of NPS responses (a
  precedent already established by the complaints pipeline's
  `raw_customer_complaint_text.sql`). The only additions were two new
  curated columns on `fact_survey_responses` (Qualtrics NPS rows only, NULL
  where `comment_text` is NULL): `comment_sentiment` (a cheap `score_0_10`
  bucket, no LLM call) and `comment_theme` (`ai_classify` against
  `comment_text`, reusing `raw_customer_complaint_event.sql`'s six-value
  category taxonomy for a consistent vocabulary with the complaint
  dashboards). Bounded cost: only runs on the ~5% of NPS rows with a
  comment (~100-150 rows in this dataset), far cheaper than the complaint
  pipeline's 15-20K-row `ai_query` pass.
- Closed-loop follow-up queue (`csat_followup_queue.sql`) filters on the
  existing `nps_bucket = 'detractor'` (already computed consistently across
  NPS/CSAT/SQM rows) rather than re-deriving score thresholds, and left-joins
  `ml_complaint_risk_scores` so a detractor who is also predicted high-risk
  surfaces as the priority call.
- Both new queries resolve `customer_id` → a single canonical `account_number`
  via `MIN_BY` over `dim_account` (active accounts preferred), so the
  "Open profile" deep-link has one deterministic target even for
  multi-account commercial customers — same grain caution as §3.
- `CsatView` finally threads a drawer callback: new `onJumpToSubject` prop
  (matching `ExplorerMap`'s existing prop name/shape exactly, over the
  `InspectorSubject` union), wired in `App.tsx` to the existing
  `setFullSubject`. "Open profile" opens the same over-map customer drawer
  used everywhere else in the app.
- Live-verified in a local dev browser session: Voice of Customer tab renders
  theme-frequency + verbatim feed with sentiment/theme badges; follow-up
  queue table renders with real detractor rows; "Open profile" opens the
  drawer with real data from both panels. Console clean.

**Phase 2 build notes (2026-07-12):**
- Response-rate denominator (§4.2): built as designed, but *additive* rather
  than reshaping `fact_survey_responses` — a new raw
  `raw_qualtrics_invitation.sql` reruns the identical NPS candidate universe
  from `raw_qualtrics_response.sql` with the same `xxhash64(survey_id,
  customer_id, 'sample'/'respond', ${random_seed})` draws, keeping the
  invited-but-silent rows the response generator discards. A new curated
  `fact_survey_invitations` aggregates it to `(survey_id, period_date_key,
  segment)` — `period_date_key` is the survey's *launch* date, not a response
  date. NPS-only: CSAT has no invited/declined step modeled (a straight 10%
  sample of interactions *is* the response), so CSAT survey health stays
  volume-only in the app, as designed. Live-verified: `n_responded` in the
  new table exactly matches the existing NPS response count per survey (by
  construction, same hash draws); response rate lands ~28–33% per quarter.
- Driver analysis (§4.4/Row 4b): the SQM sub-score columns
  (`greeting_score`/`empathy_score`/`knowledge_score`) the row calls for
  were a real gap — they existed only in raw `raw_sqm_call_evaluation`, never
  passed through to curated `fact_survey_responses`. Added as three nullable
  columns (SQM rows only), cheap and additive.
- Found and fixed a doc bug while writing `csat_operational_correlation.sql`:
  §1.3/§5 Row 1's "top-2-box = `score_0_10 ≥ 9`" is an off-by-one. The shipped
  `metric_csat` measure (Phase 1) actually uses `csat_score_1_5 >= 4` on the
  native 1–5 scale, and the 1–5→0–10 mapping used everywhere
  (`raw_qualtrics_response.sql`, `fact_survey_responses.sql`) is `score_0_10 =
  csat_score_1_5 * 2` — so 4–5 of 5 maps to `score_0_10 >= 8`, not `>= 9`.
  Phase 1's shipped SQL was unaffected (it never touched `score_0_10`
  directly); Phase 2's new queries that do touch `score_0_10` use `>= 8`.
- Operational correlation (Row 5): stayed on the star schema as directed
  (§3.5's "Phase 2 stays on the star schema" rule) — "nearest bill as of
  response date" is a row-level temporal join
  (`ROW_NUMBER() OVER (PARTITION BY response ORDER BY bill_period_end DESC)`),
  not an aggregate-only cut a metric view could express. Bill-shock buckets
  showed a roughly flat NPS/CSAT split (not a strong driver) — expected and
  honest: the synthetic generator never wired `bill_shock_pct` into the
  NPS/CSAT score model (only outage exposure and complaints were), so no
  correlation should appear; not a bug.
- UI: split `CsatView.tsx` into two tabs (reusing the `.profile-tabs` CSS
  pattern, extended to `.csat-tabs`) — "Overview" (unchanged Phase 1 panels)
  and "Drivers & Follow-up" (the three new Phase 2 panels), per §5's layout
  note. No new filters added; Phase 2 panels share the existing Period/
  Segment toolbar and params.

Goal: turn the `csat` nav item (today a generic `PlaceholderView`) into a
real, multi-panel **Customer Satisfaction & Experience** view that mirrors
what production utility CX teams actually watch, and re-home it under a
renamed **"Service & Experience"** nav section — **leaning on the data model
that already exists**, with only surgical synthetic-data additions.

## 1. Context & decisions (do not relitigate)

### 1.1 The headline finding: the data is already here

The single most important fact for the next session: **the survey / CSAT /
NPS / sentiment / driver layer already exists in the curated model.** This is
a *surfacing* project far more than a *data-modeling* project. Do NOT build a
new survey pipeline from scratch. Concretely:

| Need | Already-present source | Key columns |
|---|---|---|
| CSAT score & trend | `fact_survey_responses` (`survey_type='csat_transactional'`), `fact_csr_interactions.csat_score_1_5` | `score_0_10`, `response_date`, `response_date_key`, `csat_score_1_5` |
| NPS | `fact_survey_responses` (`survey_type='nps_relationship'`) | `score_0_10`, `nps_bucket` (promoter/passive/detractor) |
| Channel / touchpoint | `fact_csr_interactions` | `media_type` (voice/chat/email/sms), `ivr_path`, `queue`, `direction` |
| Journey / transaction type | `fact_csr_interactions.queue` / `disposition_code`; `fact_customer_complaints.category`; event-triggered surveys in `fact_survey_responses.survey_id` | `queue`, `disposition_code`, `category`, `survey_id` (outage / DSM / move-in triggers) |
| Segmentation | `dim_customer` + `dim_account` + `dim_premise` | `occupancy_class`, `building_subtype`, `city`/`county`/`county_fips`, account tenure via `dim_account`/`dim_service_agreement` |
| Survey health (volume) | `fact_survey_responses` | row counts by `survey_id`/period |
| Verbatims + sentiment | `fact_survey_responses.comment_text` (~5% of NPS + LLM `ai_query`), `fact_customer_complaints.sentiment_label`, `fact_social_mentions.sentiment_label` | `comment_text`, `sentiment_label`, complaint `category`/`sub_category` |
| Driver analysis | `fact_csr_interactions`, `raw_sqm_call_evaluation` → `fact_survey_responses` (`sqm_*`) | `wait_time_seconds`, `hold_time_seconds`, `handle_time_seconds`, `transfer_count`, `first_call_resolution_flag`, `sqm_total_score`, `sqm_fcr_flag`, greeting/empathy/knowledge sub-scores |
| Companion metrics (FCR, AHT) | `fact_csr_interactions` | `first_call_resolution_flag`, `handle_time_seconds` |
| Operational correlation | `fact_survey_responses.outage_minutes_prior_90d`/`outage_events_prior_90d`/`complaint_count_prior_90d`; `fact_outage_customer_impact`; `fact_customer_billing.bill_shock_pct` | join by `customer_id` / period |
| Closed-loop follow-up | `fact_survey_responses` low scores + `customer_id` + `agent_id` + `interaction_id` + `comment_text`; deep-link to existing profile drawer | — |
| Predicted risk (proactive) | `ml_complaint_risk_scores` (already scored, already app-wired) | `complaint_risk_tier`, `complaint_risk_pct` |

CSAT/NPS survey rows are concentrated in **2017Q1–2018Q4** (8 quarters); the
demo "now" is `2018-12-31`. `dim_date` spans 2014–2020 with ready-made
`year`/`quarter`/`month`/`month_name`/`season` columns for trend bucketing
(join on `date_key`). Legacy `fact_legacy_cx_snapshot.satisfaction_tier`
(SAP CRM, quarterly 2014–2016) and `raw_iperceptions_snapshot` (web-intercept
CSAT 2015–2016) exist but use different scales/eras — treat as optional
back-history, not the primary series.

### 1.2 Genuine gaps (small, and mostly optional)

Only four things are NOT already in the model. None require "going crazy":

1. **Response *rate* denominator.** We have response *volume* but no
   "invited/sent" count, so a true response-rate % can't be computed today.
   Fix is a lightweight synthetic addition (§4.2) — or present volume only.
2. **CES (Customer Effort Score).** Not modeled. Contact-center effort
   *proxies* exist (`transfer_count`, `handle_time_seconds`, repeat contacts).
   Recommendation: derive an effort proxy, defer a true CES survey to stretch.
3. **Web/app/field-service CSAT touchpoints.** CSAT today is
   contact-center-centric (`csat_transactional` sampled from Genesys voice/chat
   interactions; `csat_score_1_5` is voice). There is no post-web-session or
   post-truck-roll CSAT. Options in §4.3. Be honest in the UI about which
   channels are instrumented rather than faking field CSAT.
4. **Targets / external benchmarks** (internal goal, J.D. Power, ACSI). Not
   present. Cheap seed table (§4.1).

### 1.3 Decisions locked with the user (2026-07-10)

- **Nav section renamed to "Service & Experience"** (was "Business
  Functions"). CSAT moves into that group. ("CX Lenses" / "Customer Lenses"
  were considered and rejected — "lens/lenses" is already the Explorer map's
  vocabulary for metric overlays, and "CX" narrowed the tent too far for the
  Revenue/DER items.)
- **Nav label stays `"CSAT"`**; page title is the fuller **"Customer
  Satisfaction & Experience"**.
- **Headline CSAT metric = top-2-box %** (score 4–5 of 5, i.e. `score_0_10 ≥ 9`),
  with the mean as a secondary/hover value.
- **Channel breakdown ships contact-center-only** in Phase 1 (voice/chat/email/
  sms) with an honest "web/field not yet instrumented" note. Synthesizing
  web/field CSAT is stretch (§4.3 option 3).
- **Response rate is Phase 2.** Phase 1 shows response *volume* only, labeled
  honestly; the invitation denominator (§4.2) lands in Phase 2.
- **CES = effort proxy** derived from existing `fact_csr_interactions` fields
  (no data change); a true CES survey is not built. May be dropped from the KPI
  band if it reads as too hand-wavy.
- **Section membership unchanged for now**: `revenue-collections` and
  `ee-der-programs` stay under "Service & Experience" (all placeholders today);
  revisit a split once more than one becomes a real view.
- **Minimize data-model expansion.** Build the view primarily from existing
  facts; add only the small reference seed below (`ref_cx_targets`), and stage
  the rest as optional.
- Deliverable of *this* doc is the design; implementation is the next session.

## 3. App architecture — how the view is built

Follow the established pattern exactly (no new libraries needed):

- **New view file** `app/client/src/views/CsatView.tsx` (mirrors
  `DataModelView`/`MetricsCatalogView` as standalone view files; the flagship
  `ExecMap.tsx` shows the richer recharts + AppKit patterns).
- **Data fetch** via `useAnalyticsQuery<Row>("<query_name>", params)` from
  `@databricks/appkit-ui/react`, params built with `sql.*` helpers from
  `@databricks/appkit-ui/js` (see `App.tsx:2-3, 506-519`). Each panel = one
  named SQL file.
- **Query files** land in `app/config/queries/*.sql`, `{{catalog}}`/`{{schema}}`
  templated, `-- @param name TYPE` declarations with `:param` binds. They're
  auto-loaded by the `analytics()` plugin (`server.ts:8`) and copied at deploy
  (`app.yaml:9`). No server code changes for plain analytics queries.
- **Charts**: recharts is already a dependency and used throughout `ExecMap.tsx`
  (line/area/bar). Reuse the same chart primitives and the `dataviz` palette
  conventions already in `mapConstants.ts` for consistency.
- **Tabs / cards**: reuse AppKit `Tabs`/`TabsList`/`TabsTrigger`/`TabsContent`
  (as `App.tsx:527-543` does for the customer drawer) if the page is tabbed.
- **Global filters** (time range, segment, channel): local React state in
  `CsatView`, threaded into every query's params. Keep the demo default to the
  full 2017–2018 window (that's where the data lives) rather than "trailing 90d".
- **Deep-link to a customer**: the closed-loop queue rows should call the
  existing `setFullProfile(accountNumber)` path so clicking a detractor opens
  the same over-map profile drawer used elsewhere (`App.tsx:417-444`). Pass a
  callback prop into `CsatView` like `ExecMap`'s `onJumpToCustomer`.

**Grain caution (carry over the multi-site lesson):** survey/interaction facts
are keyed by `customer_id`. For any panel that segments by *location/premise*
(region, building type), resolve through `dim_account`/`dim_service_agreement`
→ `dim_premise` rather than assuming one premise per customer — multi-site
commercial chains are one `customer_id` across many premises (see the
`fact_der_adoption` premise-grain warning and `peer_monthly_usage_benchmark`
comments in the curated layer). For contact-center CSAT this mostly doesn't
bite (the interaction is customer/account-scoped), but the segmentation panel
must be premise-aware for the region/building-type cuts.

## 4. Data-model changes (minimal, phased)

### 4.1 `ref_cx_targets` — target & benchmark seed (Phase 1, cheap)

A tiny curated `CREATE OR REFRESH MATERIALIZED VIEW ref_cx_targets` built from
a `VALUES` list (same style as `dim_rate_schedule` / the survey-definition
seed). One row per `(metric, year, segment)`:

```
metric        STRING   -- 'csat' | 'nps' | 'fcr' | 'aht'
year          INT
segment       STRING   -- 'all' | 'residential' | 'commercial'
target_value  DOUBLE   -- internal goal
jdpower_value DOUBLE   -- external benchmark (nullable)
acsi_value    DOUBLE   -- external benchmark (nullable)
```

Place at `src/30_curated/transformations/ref_cx_targets.sql` (flat, under the
`transformations/**` glob — no pipeline YAML edit). No FKs needed (it's a
reference seed). Add a comment block in `src/30_curated/table_comments.py`.
Values can be plausible industry figures (CSAT target ~85% top-2-box; J.D.
Power residential electric ~700-ish scaled; ACSI utilities ~73). Used to draw
target/benchmark lines on the trend and the KPI deltas.

### 4.2 Response-rate denominator (Phase 2, optional)

To compute a real response rate, add an "invited but did not respond"
population. Lowest-touch option: extend the existing generator
`src/20_synthetic/transformations/surveys/raw_qualtrics_response.sql` to emit
an `invited` row set with a `responded_flag` (it already samples the invited
pool internally; surface the pre-filter population). Then either:

- add `invited_flag`/`responded_flag` columns into `fact_survey_responses`
  (add matching FKs, keep existing rows as `responded_flag=true`), **or**
- create a small `fact_survey_invitations` aggregate at
  `(survey_id, response_date_key, segment)` grain with `n_invited`, `n_responded`.

Recommendation: the aggregate table is cleaner and avoids reshaping the
response fact. Response rate = `n_responded / n_invited`. If we skip this,
the Survey Health panel shows **volume + trend only** and omits rate (label it
honestly). Determinism via the existing `xxhash64(..., ${random_seed})` idiom.

### 4.3 Web/app/field-service CSAT touchpoints (stretch)

Three honest options, in ascending effort:

1. **Do nothing; be explicit.** Channel breakdown covers contact-center media
   types (voice/chat/email/sms) — label the panel "Contact-center CSAT by
   channel" and add a small note that web/app/field aren't yet instrumented.
   *(Recommended for first ship.)*
2. **Reuse legacy web signal.** Surface `raw_iperceptions_snapshot`
   (web-intercept CSAT 2015–2016) as a separate faint "web (legacy)" series —
   cheap but off-era.
3. **Synthesize post-transaction CSAT** for web self-service and field/truck-roll
   by adding new `survey_type` branches (`csat_web_selfservice`,
   `csat_field_service`) into `raw_qualtrics_response.sql` + a UNION branch in
   `fact_survey_responses.sql`, sampling from `fact_digital_engagement` (web/app)
   and `fact_service_event` move-in/meter-swap (field). Highest effort; only if
   a full omni-channel channel-breakdown is a demo must-have.

### 4.4 CES (stretch)

Either derive an **effort proxy** from `fact_csr_interactions`
(`transfer_count`, repeat-contact within N days, `handle_time_seconds`) and
label it "Effort proxy" — no data change — or add a `ces_transactional`
`survey_type` branch mirroring CSAT. Recommend the proxy for now.

### 4.5 Governed metric views (Phase 1–2, cheap, high value for Genie)

Add CSAT/NPS/FCR/AHT metric definitions to the `METRIC_VIEWS` dict in
`src/30_curated/metric_views.py` so the same numbers are queryable by Genie and
the Metrics Catalog view, not just the app. This keeps "Ask the Map"/Genie
answers consistent with the CSAT page.

**Net Phase-1 data footprint:** exactly one new tiny seed table
(`ref_cx_targets`) + metric-view entries. Everything else Phase 1 reads from
existing facts.

## 5. Page layout & panels (element-by-element)

Page = `CsatView.tsx`, titled **"Customer Satisfaction & Experience"**, with a
sticky filter bar (time range · segment · channel) feeding all queries. Panels
map 1:1 to the CX elements the user listed. Each panel names its data source
and the query file to create.

### Row 1 — Companion-metric KPI band `csat_kpis.sql`
Stat tiles with sparkline + delta-vs-prior-period + delta-vs-target:
- **Overall CSAT** — headline is **top-2-box %** (`score_0_10 ≥ 9`, i.e. 4–5/5),
  mean as secondary/hover, from `fact_survey_responses` csat rows +
  `fact_csr_interactions.csat_score_1_5`.
- **NPS** — `%promoter − %detractor` from `nps_bucket`.
- **FCR %** — `avg(first_call_resolution_flag)` (× `sqm_fcr_flag`) from
  `fact_csr_interactions`.
- **AHT** — `avg(handle_time_seconds)`.
- *(optional)* **Effort proxy / CES** (§4.4).
Targets/benchmarks from `ref_cx_targets`. → covers elements #1 (score), #9
(companion metrics), #8 (benchmarks, as deltas).

### Row 2 — CSAT trend `csat_trend.sql`
Line chart, monthly ↔ quarterly toggle, with MoM/QoQ/YoY delta labels; overlay
a **target line** and **prior-year** series. Group by `dim_date.year`/`quarter`
/`month` joined on `response_date_key`. Optional faint legacy series from
`fact_legacy_cx_snapshot`/iPerceptions. → element #1.

### Row 3a — CSAT by channel/touchpoint `csat_by_channel.sql`
Bars of CSAT by `fact_csr_interactions.media_type` (+ `ivr_path` top paths).
Title honestly as contact-center channels (see §4.3). → element #2.

### Row 3b — CSAT by journey/transaction type `csat_by_journey.sql`
Bars by `queue` / `disposition_code` / complaint `category` mapped to journeys
(billing inquiry, outage, payment arrangement, new service/move-in, DSM). Use
event-triggered `survey_id` values where present. → element #3.

### Row 4a — Segmentation `csat_by_segment.sql`
Grouped bars / small heatmap: residential vs commercial (via
`dim_premise.occupancy_class`/`building_subtype`), by region
(`county`/`city`), by tenure band (from account/service-agreement start).
**Premise-aware joins** per §3 grain caution. → element #4.

### Row 4b — Driver analysis `csat_drivers.sql`
CSAT by wait-time bucket (`wait_time_seconds`), by FCR yes/no, by
transfer_count, and correlation with SQM sub-scores (empathy/knowledge/greeting
from `raw_sqm_call_evaluation` → `fact_survey_responses.sqm_*`). Present as a
ranked "what moves the score" bar (delta in CSAT for each driver level). →
element #7.

### Row 5 — Operational correlation `csat_operational_correlation.sql`
CSAT/NPS vs outage exposure (`outage_minutes_prior_90d`/`outage_events_prior_90d`
buckets) and vs bill shock (`fact_customer_billing.bill_shock_pct`). Optionally
compute simple SAIDI/SAIFI-style aggregates from `fact_outage_customer_impact`
by region and plot against CSAT. → element #10.

### Row 6 — Survey health `csat_survey_health.sql`
Response **volume** over time by survey type; response **rate** if §4.2 lands
(else volume only, labeled). Small table of n by `survey_id`. → element #5.

### Row 7 — Voice of Customer `csat_verbatims.sql`
Verbatim feed: `comment_text` with `sentiment_label` and a theme tag, most
recent / most negative first. Theme frequency bars: reuse the existing
`exec_complaint_themes.sql` theme taxonomy for complaints; for survey comments,
a lightweight `ai_classify`/`ai_query` theme tag is a Phase-3 add (comments are
~5% of NPS, so this panel is thin unless we widen comment generation). →
element #6.

### Row 8 — Closed-loop follow-up queue `csat_followup_queue.sql`
Table of low-score/detractor responses (score_0_10 ≤ 6 or csat 1–2) with
customer, account, agent, score, comment, date, and a **"Open profile"** action
that calls `setFullProfile(account_number)` to open the existing drawer. Show
the customer's `ml_complaint_risk_scores` tier inline to tie reactive
(detractor) and proactive (predicted-risk) together. → elements #11 + #12
(case management / closed-loop).

**Layout note:** Rows 1–3 are the "at a glance" fold (KPIs, trend, channel/
journey). Rows 4–8 are drill-down. Consider a two-tab split
("Overview" | "Drivers & Follow-up") using AppKit Tabs if a single scroll is
too long.

## 7. Recommended phasing

- **Phase 1 — Core (ship first).** Nav rename + move + `CsatView` scaffold;
  `ref_cx_targets` seed; metric views; KPI band, CSAT trend, channel breakdown,
  journey breakdown, segmentation. All from existing data + one seed. This
  alone is a credible utility CSAT dashboard.
- **Phase 2 — Analytics depth.** Driver analysis, operational correlation,
  survey health (with the response-rate denominator §4.2).
- **Phase 3 — Voice of Customer + closed loop.** Verbatim feed with theme
  tagging, detractor follow-up queue with drawer deep-link + predicted-risk tie-in.
- **Stretch.** Omni-channel CSAT (§4.3 option 3), true CES survey (§4.4),
  legacy back-history splice.

Deliberately left out to avoid over-building: real-time survey ingestion,
per-agent scorecards (agent data lives in `dim_agent`/Emplify and belongs in a
future "Customer Service" view, not here), and external-benchmark live feeds
(seeded constants are enough for the demo).

## 9. Caveats / realism notes

- **Trend length is short.** CSAT/NPS data is 2017Q1–2018Q4 → YoY is only
  2017-vs-2018; QoQ is 8 points; MoM within-year. Frame the default view around
  quarters; don't design a 5-year trend the data can't fill.
- **CSAT is contact-center-weighted.** Be explicit in-panel; don't imply field
  or web CSAT exists unless §4.3 option 3 is built.
- **Verbatims are sparse** (~5% of NPS carry `comment_text`). Theme-tagging
  landed in Phase 3, but the panel is still thin by row count — widening the
  `ai_query` comment rate in `raw_qualtrics_response.sql` (or adding CSAT/SQM
  comment generation) is the remaining lever if a demo needs a denser feed.
- **Keep the grain lesson**: premise-aware joins for location/segment cuts to
  avoid multi-site commercial leakage (§3).
